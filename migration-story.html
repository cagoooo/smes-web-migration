跨校去識別化公開紀錄

把「應該可以」變成
「我驗證過」

這不是某一所學校的成果報告，而是一份把校網搬遷、共構平台建置、FreeGo、 AA 送審與舊站 HTTPS 拆成可重做工作線的示範故事。校名、網址、頁數與案件資料全部由讀者自行替換。

適用：各校資訊組長 正式新站：<正式新站網址> 舊站 HTTPS：<舊站網址> 期限：依所在地官方公告
為什麼開始 接手與查證 網址角色 FreeGo 轉折 正式送審 HTTPS 工作線 給其他學校 如何交接

一、校網遷移不是「換個網址」

一所學校要從自建舊站搬到共構平台，同時準備無障礙 AA，表面上像是把文章、照片與附件搬過去； 實際上還牽涉內容盤點、網站結構、外部連結、處室資料、圖片替代文字、FreeGo、人工審查、 正式網址切換，以及舊站 HTTPS 的維持。

當專案主要由一位資訊組長維護時，最重要的設計原則不是把頁面做得多華麗， 而是每一步都能被下一個人重做、查證與交接，不依賴某個人的記憶。

12 步把送審前、送審與送審後拆開
3 種角色正式站、準備站、舊站分開記錄
3 層證據自動檢測、人工審查、標章核發不混用
1 份交接每個結論都附網址、日期與可重做方法
先說結論：FreeGo 自動檢測通過，不等於人工審查完成，也不等於 AA 標章已核發。 這條界線必須在 README、操作台與交接文件中反覆寫清楚。

二、接手後的第一課：文件先於直覺

交接文件裡最吸引人的通常是「全站通過」或「全部完成」這類結論； 但如果沒有同時寫出掃描網址、日期、範圍與原始報告，就不能判斷那是不是正式站的結果。

準備站和正式站外觀看起來一樣，並不代表即時同步；舊站能開啟，也不代表 HTTPS 憑證、轉址與內容網址都正確。 因此接手時要重新跑關鍵檢查、查 Git 紀錄，再把每一個結論分成可驗證的證據。

第一步
讀專案規範、交接文件與官方流程，先找出哪些事情不能自行決定。
第二步
確認目前使用的是正式新站、共構準備站或舊站，不用漂亮截圖代替網址證據。
第三步
重新跑一次關鍵檢查，把「測試結果」「正式實測」「官方案件狀態」分成三層紀錄。

三、三個網址，三種身分

網址角色在專案中的用途不能混用的證據
<正式新站網址>正式內容、FreeGo AA 掃描與標章申請其他站的頁數與報告不能代替正式站結果
<共構準備站網址>建置、測試、比對與內容準備外觀相同不代表與正式站即時同步
<舊站網址>保留歷史內容或提供過渡期間存取舊站 HTTPS 不等於新站 AA，也不應混跑
最穩定的切法：正式新站做 AA；舊站另做 HTTPS；準備站只作建置與比對。 每份報告開頭都先寫清楚「這是哪個網址、哪一天、哪個範圍」。

四、FreeGo 的轉折：檢測 → 找問題 → 修正 → 重測

本機對比度工具或瀏覽器檢查很適合找線索，但不是官方判定本身。 看到一個色彩數字就全站換色，可能破壞共用主題並製造新的問題；正確做法是先確認實際渲染結果與影響範圍。

正式 FreeGo 檢測時，先輸入正式新站網址，選全網站與 AA，並保存掃描日期、頁數、逾時頁面、 違規代碼與排除條件。修正後要用同一個正式網址重新測，才能比較前後結果。

判讀原則：「自動部分通過」只表示工具完成了它能自動檢查的部分； 鍵盤操作、內容語意、表單、替代文字與人工判斷仍可能在官方審查中被要求改善。

五、從自動檢測走到正式送審

自我評量不要照抄別校答案。應依正式新站的實際頁面，逐項確認 PDF 是否能選取文字、鍵盤操作、 跳至主內容、圖片／輪播、表單標籤、驗證與響應式呈現，再填入審查員能重現的位置。

送出後看到「待指派」時，代表案件進入等待官方分案或審查的階段； 它不是「送出失敗」，也不是「標章已核發」。案件畫面、送出日期與官方通知都應保存為證據。

送出前確認

  • 網址是正式新站，不是準備站或測試站
  • 網站名稱、機關代碼與標章等級正確
  • 固定導覽文字沒有自行改寫
  • 自評內容能由實際頁面重現

送出後記錄

  • 案件畫面與送出日期
  • FreeGo 設定與校內報告位置
  • 官方狀態與通知內容
  • 修正、重測與回覆的 Git／文件紀錄

六、舊站 HTTPS 是獨立工作線

如果舊站要保留，HTTPS 應拆成另一張工作清單：先確認 DNS 解析，再查 CAA／DNSSEC、 ACME 驗證、網頁伺服器的主機名設定、現有憑證與公開 TLS 回應。

遇到 DNS SERVFAIL 時，不要只是不斷重試憑證申請；先用多個公開 DNS 查詢確認權威解析， 再依序排除 DNS、CAA、伺服器設定與憑證部署問題。最後要用公開請求驗證 HTTP 轉址、HTTPS 狀態、 subject、issuer、SAN 與有效期限。

安全邊界：憑證成功不代表可以直接把舊站資料庫中的所有網址全域取代。 內容網址切換需要另開決策、完整備份、影響盤點與回復計畫。

七、給其他學校的十個可複製原則

  1. 先讀規範再碰網站。先找出不可自行決定的事項。
  2. 正式站、準備站、舊站分開命名。外觀相同不代表同步。
  3. 每個數字附來源、網址與日期。沒有證據的「全過」不能放進交接。
  4. FreeGo 不等於標章。自動檢測、人工審查、核發是三階段。
  5. 色彩警示先分類。先看實際畫面，再決定是否改。
  6. 先修共用問題。一個共用元件可能影響大量頁面。
  7. AA 與 HTTPS 分線。新站無障礙和舊站安全性各自驗證。
  8. DNS 問題先查權威解析。不要盲目重試 ACME。
  9. 每次修改留下回復方式。報告、指令、commit 與實測回應都要可追溯。
  10. 公開分享前做去識別化掃描。不要發布校名、網域、個資、帳密或案件編號。
最小可複製流程： 盤點 → 分清網址角色 → 修共用問題 → 用正式網址跑 FreeGo → 依實際頁面填自評 → 送出後等待指派 → 舊站另做 HTTPS → 用公開請求驗證 → 寫入校內交接文件。

八、如何把這份教材套到你的學校

先複製線上操作台的 12 步驟，建立校內版證據表；再把三個網址、FreeGo 報告、 自我評量畫面、修正 commit 與官方通知填進去。公開版只保留流程與格式，校內版才保存真實資料。

遇到問題時，不要只寫「失敗」：請記下網址、時間、瀏覽器／工具版本、輸入條件、 實際錯誤文字、已嘗試的修正與下一步。下一位資訊組長才能從同一個現象繼續，而不是重新猜一次。

這份故事集真正想留下的，不是某校的成功截圖： 而是如何把不確定性拆開、讓每一步都有邊界、有證據、有回復方式， 讓任何學校都能依自己的平台與網址重做。

公開紀錄的安全邊界

本分享版刻意不列出任何單一學校名稱、學校網域、教職員姓名、Email、電話、 FreeGo 上傳編號、官方案件識別碼、帳密、伺服器路徑或個案附件。 請不要把這些資料補回公開 repository。

無障礙申請細節請以數位發展部官方平台與所在地主管機關最新公告為準； 共構平台使用者也應先閱讀所在地平台的官方總目錄與申請流程。
