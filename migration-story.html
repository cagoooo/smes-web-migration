一、這件事一開始，並不是「換個網址」這麼簡單

石門國小原本有一套自建 XOOPS 舊校網，接著要搬到教育局的 XOOPS 共構平台， 同時還要準備申請無障礙標章 AA。表面上看起來像是把文章、照片、附件搬過去； 實際上卻同時牽涉內容盤點、網站結構、外部連結、處室資料、圖片替代文字、 FreeGo 自動檢測、人工審查、正式網址切換，以及舊站的 HTTPS 維持。

更現實的是，這是一個由一位資訊組長長期維護的校務專案，不是有專職工程團隊 可以把所有事情拆給不同人。於是第一個設計原則很快確立： 每一步都要能被下一個人重做、查證、交接，而不是只存在某個人的記憶裡。

先說結論：截至這份故事集更新時，正式 www 已完成 FreeGo 自動檢測與 AA 自我評量送出，案件狀態是「待指派」；舊 web 已拿到 Let’s Encrypt 憑證。 AA 標章本身仍要等官方後續審查，不能把「自動檢測通過」寫成「標章已取得」。

二、接手後最先學到的教訓：文件先於直覺，正式站先於漂亮截圖

前一個 agent 交接時留下了不少數字，其中最吸引人的，是「184 頁全過」。 但接手後沒有直接把這個數字當成事實，而是先依序閱讀專案規範、交接文件與補齊清單， 再重新跑檢查、查 Git 紀錄、看目前的網址。

查證後才發現，那個 184 頁結果來自準備用的 schoolweb2， 不是審查委員會真正會看到的正式 www。兩個站外觀看起來很像， 並不代表它們即時同步；更不能把準備站的通過結果直接移植成正式站證明。

這個差異看似只是網址多了 2，實際上卻是整個專案的證據邊界： 後來所有 FreeGo 與 AA 送審判斷，都改以正式 www 為準；準備站只保留為參考， 不再混用兩邊的頁數、報告與完成狀態。

第一步
讀規範、交接與執行清單，先知道哪些事情不能自作主張。
第二步
重新跑檢查，確認腳本曾經打錯網址的技術債，並把三支核心腳本改成正式 www／舊站 web。
第三步
把「測試站結果」「正式站實測」「官方案件狀態」分成三種證據，不再用一句「看起來一樣」代替驗證。

三、三個網址，三種身分：先把角色講清楚，後面才不會互相污染

網址在專案中的角色這次怎麼使用
www.smes.tyc.edu.tw 正式新校網 所有正式內容、FreeGo AA 掃描與官方標章申請都以此為準。
schoolweb2.tyc.edu.tw/~smes_www 準備／共構平台網址 用來協助建置與比對；外觀相似不代表與正式站即時同步。
web.smes.tyc.edu.tw 保留的舊校網 本次只處理 Let’s Encrypt HTTPS，不納入 AA 檢測範圍。
一個很容易犯的錯：把新站的 AA 工作和舊站的網址／憑證工作混成一件事。 這次刻意拆成兩條線：www 做 AA；web 做 HTTPS。 這個切法讓問題變小，也讓每一次驗證都知道自己在證明什麼。

四、FreeGo 的轉折：不是看到警示就全部改色，而是做「檢測 → 找問題 → 修正 → 重測」

專案中途，本機對比度工具曾列出多組警示。直覺反應很容易是把所有顏色全部重做； 但實際經驗告訴我們，本機工具比較適合當「找線索」工具，不是官方判定本身。 如果沒有先看實際渲染結果，就可能為了誤判大幅改動共用主題，反而製造新的問題。

真正的轉折來自 FreeGo 正式站重測。前一輪報告指出「石門網路教學資源」區塊 有一個沒有可讀文字的空白連結；同時首頁滑動圖片的替代文字也完成手動修正。 修正時沒有把整個區塊推倒重做，而是精準移除空白 <a>， 保留有文字的正常連結，再用正式 www 重新跑完整網站。

五、從自動檢測走到正式送審：最重要的是填真實狀況，不是把表格填漂亮

FreeGo 完成後，專案進入官方無障礙平台的申請與自我評量。這裡沒有用猜的： 依照正式 www 的實際頁面逐項確認 PDF 是否能選取文字、鍵盤操作與跳至主內容、 圖片／輪播、表單標籤與驗證、響應式呈現等，再把頁面位置填成可被審查員重現的首頁或對應頁面。

申請表需要 FreeGo 上傳編號時，從本機既有檢測產物核對，不把編號寫進公開故事集。 送出自我評量後，平台案件顯示為「待指派」。這表示資料已送進官方流程， 下一階段是等待軟體與人工審查，不是繼續無限增加內容。

送審策略的反直覺之處：研習與中心反覆提醒，網站做得越滿， 人工審查時可被挑出的地方就越多。因此送審前不是「把所有想法都做完」， 而是先把核心結構、必要內容與可驗證的無障礙設計做穩。

六、web 舊站的獨立戰線：三次 SERVFAIL，最後把 HTTPS 做到可驗證

舊站改保留為 web.smes.tyc.edu.tw 後，最初並沒有立刻成功拿到憑證。 Let’s Encrypt 曾連續遇到 DNS SERVFAIL；但從學校端用多個公開 DNS 查詢時， 解析結果又穩定一致。這段最容易誤判成「一定是我們設定錯了」，也最容易在短時間內 不斷重試，把 ACME 失敗次數用光。

做法是先停下來，把 DNS、CAA、DNSSEC、nginx server_name、現有憑證與公開解析分開確認。 這些檢查沒有把責任推給某一個猜測；它們只回答一個個小問題： 網域有沒有解析？憑證授權有沒有被 CAA 擋住？nginx 目前服務哪個主機名？ 舊站的 HTTPS 是否真的由正確憑證回應？

後來正式簽發成功，並由 nginx 掛上 /etc/letsencrypt/live/web.smes.tyc.edu.tw/ 的憑證與私鑰。 過程中曾有一次把備份暫放進 nginx 啟用目錄，造成重複 listen 的測試錯誤； 立即把備份移回專用備份位置，重新執行設定檢查與 reload，最後服務恢復到正確狀態。

最後不是看瀏覽器「好像安全」：用公開請求確認 HTTP 回應是 301， HTTPS 回應是 200；再用 TLS handshake 讀取 subject、issuer、SAN、有效期限。 憑證驗證和網頁內容驗證，兩者都通過才算這條工作線完成。

七、如果其他學校要照著做，我最推薦先記住這十件事

  1. 先讀交接與規範，再碰網站。尤其是「不要動的地方」與「必須問本人」的決策。
  2. 把準備站、正式站、舊站分開命名。外觀一樣不代表資料同步，報告也不能混用。
  3. 所有數字都要附來源、網址、日期。「184 頁」如果沒有說明是哪個站、哪一天，就不能當證據。
  4. FreeGo 是自動檢測工具，不是人工標章核發器。自動通過、送出申請、取得標章是三個階段。
  5. 本機警示先分類。先看實際 CSS 與渲染，再決定要不要改，不要看到顏色數字就全站換色。
  6. 先修共用問題，再修個別內容。一個空白連結或版型問題可能在數百頁重複出現。
  7. 舊站 HTTPS 與新站 AA 分成兩條工作線。一條完成不代表另一條完成，也不應互相拖延。
  8. 憑證問題先看 DNS，再看 ACME。公開解析、CAA、權威 DNS、nginx 與 TLS 要各自驗證。
  9. 每次修改都留下可重做的證據。報告、指令、Git commit、公開頁面與實測回應缺一不可。
  10. 公開分享前做一次隱私掃描。教職員名單、Email、電話、帳密檔案永遠不應進公開 repo。
一個可複製的最小流程： 盤點 → 分清網址角色 → 修共用問題 → 以正式網址跑 FreeGo → 依實際頁面填自評 → 送出後等待指派 → 舊站另做 HTTPS → 用公開 HTTP/TLS 請求驗證 → 把結果寫進交接文件。

八、故事還沒有結束：現在停在「待指派」，不是停在「不知道怎麼辦」

目前最重要的工作不是再製造更多變更，而是保留正式 www 的內容穩定性， 等待官方案件指派與審查通知。如果官方要求改善，就依通知內容逐項修正、重測、 回覆；如果沒有要求，就不要為了追求「看起來更完整」而自行擴大送審範圍。

舊站 web 已經有正常 HTTPS，但舊站 XOOPS 設定與資料庫裡的舊 www 內容網址， 尚未全面改成 web。這件事如果要做，必須另開內容網址切換工作，先完整備份， 再確認哪些外部連結、圖片、相簿與自製小站應該保留。憑證成功，不代表可以直接 對資料庫做全域取代。

這份故事集的真正主題：不是「AI 幫忙把網站做完」，而是把一個 真實校務專案中的不確定性拆開，讓每一步都有邊界、有證據、有回復方式， 也讓下一位資訊組長不必從零開始猜。
